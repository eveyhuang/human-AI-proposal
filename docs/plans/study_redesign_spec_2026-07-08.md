# Study Redesign Spec

Date: 2026-07-08

This document is a concrete no-code redesign spec for the proposal-generation,
review-generation, and analysis pipeline used in this project. It is written to
integrate:

- the feedback in `docs/feedbacks/pnas-review-feedback-2026-07-07.md`
- the current execution-status plan in `docs/plans/analysis_plan.md`
- the current template notebooks in `notebooks/templates/`
- the current rendering/orchestration code in `src/notebook_pipeline.py`
- the current generation, rephrasing, and preparation scripts in `src/`

The goal is to make the study cleaner, more defensible, and easier to run and
audit, while preserving the strongest parts of the current project.

## 1. Main Goals

The redesigned study should answer below research questions cleanly:

1. How do AI-generated proposal sets compare to human proposal sets in terms of diversity and novelty (relative to a literature corpus in human-AI-proposal-comparison/data/literature/relevant-corpus-from-pubmed.json)? Compare across these three conditions for AI generation:
  1a. Baseline condition: each AI model generates 23 ideas all at once in one sample
  
  1b. One-at-a-time condition: each AI model sampled indepdently to generate 1 idea a time; and called 23 times in total to generate the whole set;
  
  1c. persona condition: Each AI model sampled independently and given a set of persona cards that match the human scientists' profiles for each proposal; using persona cards ('human-AI-proposal-comparison/data/literature/persona_cards.json')

  For each condition, compare these in analyses:
    - Diversity between human proposal set and proposal sets generated by each AI model 
    - Diversity between human proposal set and proposal sets by ALL AI models pooled (but match the same N for human proposals through sampling and bootstraping)

2. How do AI-generated review sets comapre to human review sets in terms of diversity?
  2a. Baseline review condition: Each AI model generates 5 reviews for each
  *human proposal* in one batched response, using only the NCEMS criteria.

  2b. One-at-a-time review condition: Each AI model generates 5 reviews
  (indepdent calls, one at a time, only given the NCEMS criteria) for each
  *human proposal*.

  2c. persona review condition: Each AI model generates 5 reviews
  (indepdent calls, one at a time, given the NCEMS criteria and persona cards)
  for each *human proposal*; the goal is to simulate reviewer heterogeneity by
  giving the model different human-scientist perspectives
  
  for each condition, compare these in analyses:
    - Compare the diversity of reviews from a single model to human reviewer panels when matched exactly on number of reviews per proposal.
    - Compare the diversity of reviews from a panel of AI reviews pooled across
      the 3 models, when matched exactly on number of reviews per proposal. The
      pooled AI panel should always be sampled from the full 15-review
      reservoir: 5 reviews per model.
  

## 2. High-Level Design Principles

  - 1_gen_proposals.ipynb: Generate AI ideas and proposals for **each condition**; keep them saved in seperate csv files in 'human-AI-proposal-comparison/data/ai-proposals/{condition}'.

  - 6a_compare_reviews_original.ipynb: do all the diversity-related anlayses in human-AI-proposal-comparison/notebooks/templates/rephrased/compare_reviews_ncems_criteria.ipynb but for original reviews and compare acorss conditions. core target is diversity, not score quality. the notebook should produce both:
    - per-model results within each condition
    - pooled-AI-within-condition results

  - 6b_compare_reviews_rephrased.ipynb: do all the diversity-related anlayses in human-AI-proposal-comparison/notebooks/templates/rephrased/compare_reviews_ncems_criteria.ipynb but for rephrased reviews and compare acorss conditions. core target is diversity, not score quality. the notebook should produce both:
    - per-model results within each condition
    - pooled-AI-within-condition results

### Things to update or keep:
 
1. For all diversity metrics derived from shared within-group distance
matrices, pay attention to i.i.d; for metrics that violate i.i.d:

  - primary inference must be permutation-based
  - permutation p-values are the headline values
  - Mann-Whitney values may be retained only as secondary descriptive context

  This rule applies to proposal-side matrix-derived diversity metrics and any
  other analysis where the compared values are functions of one shared
  distance/adjacency matrix. It does not override proposal-level paired review
  analyses like the exact-n matched review-diversity notebooks, where the
  inferential unit is one independent target proposal and paired Wilcoxon is the
  correct primary test.

2. Update the LLM models used in "human-AI-proposal-comparison/src/ai_models_interface.py" and all the idea, proposal, review generation to the newest frontier models if they are not already. As of 2026-07-08, the intended canonical study model IDs are: `gemini-3.1-pro-preview`, `gpt-5.5`, and `claude-sonnet-5`.

3. Stick to this visualization design guide: 
  ## Data Visualization Guide

This guide summarizes the visual conventions used in the audited `baseline(minimal)-rephrased/compare_proposals_rephrased.ipynb` notebook and should be treated as the default style for future condition notebooks unless an analysis requires a specific exception.

### Color Scheme and Metadata Encoding

- Use the shared group palette consistently: Human `#DC143C`, Claude `#4A90E2`, Gemini `#7B68EE`, GPT `#3CB371`.
- Use `#808080` only as a fallback for unknown groups. Combined All-AI views use Claude blue `#4A90E2` for stronger contrast from the Human red palette.
- Proposal-level Human funding status should be encoded as an outline/ring rather than a second red fill: funded Human proposals use a magenta ring `#FF00FF` around the base Human-colored point. Nonfunded or unknown-funding Human proposals keep the ordinary Human point fill with no funding ring.
- Top-ranked proposals should be marked with a black outline/ring only when a valid ranking field exists, typically `is_top5_ranked` on the Human proposal side. This applies to both boxplot jitter points and UMAP/scatter proposal markers. If a point is both funded Human and top-ranked, show both encodings as nested rings, with the funded magenta ring inside the top-ranked black ring.
- When deriving `is_top5_ranked` from review ranks, select the five smallest rows with `nsmallest(5)` or an equivalent stable top-k operation rather than filtering on `rank <= 5`; averaged tie ranks can skip values and otherwise yield fewer than five highlighted proposals.
- In the redesigned study, AI proposals should not receive review-derived ranking overlays because AI proposal reviews are no longer generated. Human top-ranked markers should come from the Human ranking field only, not from any mixed Human+AI rank.
- Outlier overlays should use outline rings rather than replacing the base point color. Proposal-space or within-cluster outliers use magenta outlines; literature-space comparison overlays may use an additional cyan outline when two outlier definitions are shown together.
- Literature-background points in literature-space UMAPs should remain small and semi-transparent so proposal markers and BERTopic region labels remain visually dominant.
- Whenever used, legends should explicitly explain black top-ranked outlines, magenta funded-Human rings, outlier rings, and any literature-region colors that are needed to interpret the panel.

### Standard Boxplot Grammar

Use the standardized boxplot helper pattern for all group-comparison distributions.

- Box: standard median line, IQR box, whiskers, and outlier points. Fill each box with the group color at 70% opacity and use black outlines/median lines.
- Jittered scatter: overlay individual observations with random horizontal jitter of approximately `±0.15` units, point size around `20`, and 50% opacity. Use the same group color for the point fill. When proposal metadata are available, add a magenta ring for funded Human proposals and a black ring for top-ranked proposals.
- Mean + 95% CI: plot the bootstrapped mean as a filled diamond marker of roughly `50` points, with vertical error bars for the 95% bootstrap confidence interval. Draw this above jitter points.
- Proposal-level panels should preserve `proposal_uid` or equivalent metadata columns through reshaping/melting so funding and top-rank encodings survive into the plotting layer.
- Non-proposal observations, such as pairwise distances or CV folds, should still use the standardized box/point/mean-CI grammar but should not force proposal-level funding or ranking metadata onto datapoints that do not represent a single proposal.
- Grouped metric panels, such as novelty metrics across multiple `k` values, should use dodged standardized boxplots with a group legend and the same metadata legend when proposal-level rows are available.

### Violin, Ridge, and Histogram Views

- Violin plots should be used sparingly as descriptive distribution-shape diagnostics, not as the primary group-comparison figure when inferential interpretation is expected. For proposal metric comparisons, prefer the standardized boxplot grammar above.
- If a violin plot is used, it should follow the same group palette, show median/quartile or mean annotations clearly, and avoid duplicating an adjacent standardized boxplot unless the shape view adds information.
- Ridge plots are appropriate for dense pairwise-distance distributions where the full shape and skew are important. Use group-colored density fills, with solid median and dashed mean lines in the same group color.
- Histograms should use consistent binning across groups, transparent fills, and log-scale counts when long tails obscure most of the distribution. They should be labeled as descriptive full-range views.

### UMAP and Embedding-Space Projections

- Reuse cached UMAP coordinates whenever available. Proposal-space UMAPs should load the condition- and text-branch-specific cache produced by `4a_prepare_proposal_for_analysis.ipynb` or the relevant downstream shared-cache directory. Literature-space UMAPs should use the fixed literature reducer and coordinates from `data/embeddings/literature/lit_umap_reducer.pkl` and `data/embeddings/literature/lit_umap2d.npy`.
- Literature-space UMAPs and BERTopic-region overlays must project Section-1 / abstract-only proposal embeddings, not full-proposal embeddings. This keeps proposal markers comparable to the literature abstract embeddings and to the proposal-to-literature novelty metrics.
- Do not refit UMAP inside a visualization cell if a cache exists. If recomputation is unavoidable, use the documented parameters and save the cache for downstream panels.
- Axis labels should identify the coordinate system: `UMAP-1` / `UMAP-2` for proposal-space maps, and `Literature UMAP Dim 1` / `Literature UMAP Dim 2` for literature-anchored maps.
- Proposal markers should follow the metadata encoding above: AI groups use the group palette; Human uses the Human palette color; funded Human proposals add a magenta ring; Human top-ranked proposals may add black outlines when valid Human ranking metadata exist. AI proposals should use black ranking outlines only if a later notebook explicitly defines a separate analysis-derived overlay and labels it clearly as such.
- Per-cluster UMAP zooms should retain the same marker semantics and use panel titles with cluster names, total `n`, and compact discriminative topic labels when available.
- Literature-region UMAPs should color the fixed literature background by BERTopic embedding-region labels, not LDA lexical topics. LDA-colored maps are supplementary diagnostics only.
- UMAP legends should explicitly explain black top-ranked outlines, magenta funded-Human rings, outlier rings, and any literature-region colors that are needed to interpret the panel.

### Effect-Size and Significance Panels

- Pair distribution panels with statistical comparisons should be paired with an effect-size panel when space allows.
- Cliff's delta panels should use a vertical zero reference line, horizontal CIs, and group-colored markers for the model-vs-Human contrast.
- Label effect-size axes with the direction of the comparison, e.g. `Cliff's δ (bootstrap 95% CI)` or `AI − Human`. If positive/negative direction changes by metric, state that in the axis label or caption.
- Significance stars should reflect corrected p-values where correction is part of the analysis. Use the compact table convention: `*** p<.001`, `** p<.01`, `* p<.05`.

### Labels, Legends, and Export Standards

- Titles should name the analysis object and, when useful, include a second line describing key encodings such as `diamond/error bar = mean bootstrap 95% CI`.
- Axis labels should use metric units or definitions rather than variable names. Examples: `Pairwise cosine distance`, `Distance to group centroid`, `Cosine distance to global centroid`, `Nearest-Neighbor Distance`, `Unique MeSH descriptors`.
- Include sample sizes in tick labels, panel titles, legends, or adjacent tables when group size differences could affect interpretation.
- Use legends only when they decode colors, markers, line styles, or rings. Place legends outside or below crowded panels when they would obscure data.
- Use light grids for quantitative y-axes (`alpha` around `0.2-0.3`) and avoid heavy gridlines on embedding maps.
- Save figures under the appropriate condition-specific `results/figures/...` directory with descriptive filenames, `dpi` at least `200` for notebook diagnostics and `300` for manuscript-style figures, and `bbox_inches='tight'`.



## 3. Detailed Redesign For `1_gen_proposals.ipynb`

This section is the concrete redesign spec for the proposal-generation stage.
It uses the current `notebooks/templates/gen_proposals.ipynb` only as source
material. The new working notebook should be `notebooks/1_gen_proposals.ipynb`,
and it should not depend on `src/notebook_pipeline.py` or any auto-injected
condition cells.

### 3.1 Scope

`1_gen_proposals.ipynb` should do exactly two things:

1. Generate AI ideas for each proposal-generation condition.
2. After all ideas are finished and saved, expand those ideas into full AI
   proposals using the same model that generated each idea.

It should not:

- run rephrasing
- prepare embeddings
- compare proposals
- depend on condition-specific rendered notebooks
- mix proposal generation with review generation

### 3.2 Conditions This Notebook Must Support

The notebook should generate proposals for exactly these three conditions:

- `baseline`
  - one batch call per model
  - `23` ideas returned in a single response
  - prompt family based on the current minimal prompt
  - temperature `0.9`

- `one_at_a_time`
  - `23` independent calls per model
  - each call returns exactly `1` idea
  - same minimal prompt family, but rewritten for single-idea generation
  - temperature `0.9`

- `persona`
  - `23` independent calls per model
  - each call returns exactly `1` idea
  - each call uses one persona card matched to one human team/proposal
  - temperature `0.9`

The notebook should derive the target proposal count from the human comparison
set or persona-card file once at the start, validate that it is currently `23`,
and then use that same `N` everywhere instead of hard-coding `23` in multiple
cells.

### 3.3 Required Execution Order

The current template notebook generates ideas and then immediately expands them
within one condition. That is no longer the correct design.

The new notebook must run in two global passes:

1. Pass A: generate and save all ideas for all requested conditions.
2. Pass B: only after Pass A is complete, load the saved ideas and expand all
   ideas into full proposals.

This ordering matters because the study design now treats idea generation as
its own stage. It prevents proposal-generation failures from changing the idea
generation schedule or making one condition more incomplete than another.

### 3.3A Input Data Contract

`1_gen_proposals.ipynb` should take the following data inputs.

Required shared source files:

- `data/call_and_info.json`
  - provides the funding-call text and NCEMS background text used in every idea
    and proposal prompt

- `data/human-proposals/human-proposals-y1.json`
- `data/human-proposals/human-proposals-y2.json`
  - used to define the human comparison set size, validate that the target
    proposal count is currently `23`, and recover proposal-level metadata when
    needed for persona alignment and downstream provenance

- `data/literature/persona_cards.json`
  - required for the `persona` condition
  - used to map each persona-conditioned AI idea/proposal to one human team

Optional same-stage resume inputs:

- `data/ai-proposals/{condition}/ai_ideas_{condition}_*.csv`
- `data/ai-proposals/{condition}/ai_proposals_{condition}_progress_*.csv`
- `data/ai-proposals/{condition}/generation_manifest_{condition}_*.json`
  - used only when `RESUME_OK=True`
  - must be limited to the same condition being resumed

The notebook should normalize these files into a small set of in-memory data
objects before generation starts:

- `shared_call_context`
  - `research_call`
  - `information_about_ncems`

- `human_target_roster`
  - one row per human proposal
  - includes:
    - `target_cohort`
    - `target_proposal_id`
    - `target_proposal_uid`
    - `target_proposal_title`
    - `target_proposal_status`
    - `target_authors`

- `persona_roster`
  - one row per persona card
  - includes:
    - `persona_card_id`
    - `persona_team_id`
    - `source_human_proposal_id`
    - `source_human_proposal_title`
    - `cohort`

- `proposal_condition_registry`
  - one config object per proposal condition

No other notebook should be required to run before `1_gen_proposals.ipynb`.

### 3.4 Required Notebook Structure

The current `notebooks/templates/gen_proposals.ipynb` should be reworked into
`notebooks/1_gen_proposals.ipynb` with these sections:

1. `## Configuration`
   - choose `CONDITIONS_TO_RUN`
   - choose `MODELS_TO_USE`
   - set `GENERATION_TEMPERATURE = 0.9`
   - set `MAX_RETRIES`, `SAVE_PROGRESS_EVERY_N_CALLS`, and `RESUME_OK`
   - define paths for `data/ai-proposals/` and persona cards

2. `## Environment Validation`
   - validate imports and API keys
   - print available models and resolved project root
   - do not run `pip install` inside the notebook as part of routine execution

3. `## Load Shared Inputs`
   - load `call_and_info.json`
   - load human target count
   - load persona cards once and validate one card per human proposal when
     `persona` is selected

4. `## Build Condition Registry`
   - construct one explicit config object per condition
   - each config should state:
     - condition name
     - idea prompt template name
     - proposal prompt template name
     - idea generation mode (`batch` or `independent_single`)
     - whether persona cards are used in idea generation
     - whether persona cards are reused in proposal expansion
     - expected rows per model

5. `## Pass A: Generate Ideas`
   - loop over condition, then model, then call schedule
   - save condition-specific idea CSVs and failure logs
   - do not begin proposal expansion here

6. `## Quality Checks For Ideas`
   - verify exact row counts per condition and per model
   - verify one idea per independent call
   - verify parsed title and abstract are present
   - flag duplicates but do not deduplicate automatically

7. `## Pass B: Expand Ideas Into Full Proposals`
   - load the frozen idea CSV for each condition
   - generate full proposals with the same model that produced each idea
   - for persona condition, reuse the same persona card during expansion
   - save progress and only mark a file complete when every row is complete

8. `## Final QA Summary`
   - counts by condition and model
   - failure counts and retry counts
   - paths of output files
   - completion status

The current notebook cell that calls `src/rephrase_proposals.py` at the end
must be removed. Rephrasing is handled later by `3_rephrase.ipynb`.

### 3.5 Changes Needed In The Notebook Logic

The current template notebook mixes several incompatible workflows:

- generate new ideas
- load arbitrary pre-existing idea files
- resume progress
- optionally run rephrasing
- handle baseline and persona logic inside the same inline cells

For the redesigned study, `1_gen_proposals.ipynb` should be simplified to a
generation notebook, not a general file-loader notebook.

Specific changes:

- Remove the `GENERATE_NEW_IDEAS`, `IDEAS_FILE_OVERRIDE`, and `IDEAS_GLOB`
  workflow from the main execution path.
- Replace the single `CONDITION = 'minimal'` assumption with an explicit loop
  over the three study conditions.
- Remove `RUN_REPHRASE_AT_END`.
- Replace `temperature=0.7` with `temperature=0.9` for both idea generation
  and proposal expansion.
- Stop using condition-specific text like "Baseline Condition" in markdown
  cells; the notebook must describe the full study-generation stage.
- Stop treating `author` as the main condition-control field. Keep it only for
  downstream compatibility if needed, but add explicit metadata columns instead.
- Do not silently drop malformed rows after parsing. Failed calls must be
  logged as failures and either retried or left visibly incomplete.
- Do not write a `complete` proposals CSV if required proposal sections are
  still missing. In that case only `progress` and failure logs should exist.

### 3.6 Required Output Layout

Each condition must write to its own folder:

- `data/ai-proposals/baseline/`
- `data/ai-proposals/one_at_a_time/`
- `data/ai-proposals/persona/`

Within each condition folder, the notebook should produce:

- `ai_ideas_{condition}_{run_id}.csv`
- `ai_ideas_{condition}_{run_id}_failures.csv`
- `ai_proposals_{condition}_progress_{run_id}.csv`
- `ai_proposals_{condition}_complete_{run_id}.csv`
- `ai_proposals_{condition}_{run_id}_failures.csv`
- `generation_manifest_{condition}_{run_id}.json`

The filename contract `ai_proposals_{condition}_complete_*.csv` should be
preserved so later stages can find the latest completed proposal file without
special-case logic.

### 3.7 Required CSV Schema

The current notebook writes one evolving DataFrame that begins as ideas and is
later augmented with proposal sections. That basic idea can stay, but the row
schema must become explicit and stable.

The final proposal CSV for each condition must preserve these existing text
columns for downstream compatibility:

- `model`
- `title`
- `abstract`
- `background_and_significance`
- `research_questions_and_hypotheses`
- `methods_and_approach`
- `expected_outcomes_and_impact`
- `open_science_and_reproducibility`
- `budget_and_resources`

In addition, every row should carry the following provenance and condition
metadata:

- `proposal_uid`
- `run_id`
- `condition`
- `model`
- `author` if backward compatibility requires it
- `idea_generation_mode`
- `idea_call_id`
- `idea_position_in_call`
- `idea_draw_index`
- `idea_prompt_template`
- `idea_prompt_version`
- `idea_temperature`
- `idea_generated_at`
- `proposal_call_id`
- `proposal_prompt_template`
- `proposal_prompt_version`
- `proposal_temperature`
- `proposal_generated_at`
- `persona_card_id` (nullable)
- `persona_team_id` (nullable)
- `persona_team_authors` (nullable)
- `source_human_proposal_id` (nullable)
- `source_human_proposal_title` (nullable)

Two provenance fields are especially important and should not be skipped:

- `idea_call_id`
  - in `baseline`, all 23 ideas from a model share the same call id
  - in `one_at_a_time` and `persona`, each row has its own call id

- `idea_position_in_call`
  - in `baseline`, this is `1..23`
  - in the independent conditions, this is always `1`

These fields make the sampling design auditable later.

### 3.7A Downstream Export Contract

`1_gen_proposals.ipynb` should export a small, stable set of artifacts that
later notebooks can reuse without needing to regenerate anything.

Primary exported artifacts per condition:

- `data/ai-proposals/{condition}/ai_ideas_{condition}_{run_id}.csv`
  - archival record of generated ideas
  - used for:
    - generation QA
    - appendix or mechanism analyses focused on ideas before full expansion
    - resuming proposal expansion if needed

- `data/ai-proposals/{condition}/ai_proposals_{condition}_complete_{run_id}.csv`
  - canonical original AI proposal file for that condition
  - must be the main downstream handoff artifact
  - used by:
    - `3_rephrase.ipynb` as the source for AI proposal rephrasing
    - `4a_prepare_proposal_for_analysis.ipynb` as the source for original AI
      proposals
    - any proposal-level audit or descriptive notebook that needs the original
      texts and provenance

- `data/ai-proposals/{condition}/generation_manifest_{condition}_{run_id}.json`
  - machine-readable summary of prompts, temperatures, counts, failures,
    timestamps, and completion state
  - used for:
    - reproducibility checks
    - manuscript methods reporting
    - QA before downstream notebooks run

Secondary exported artifacts per condition:

- `data/ai-proposals/{condition}/ai_ideas_{condition}_{run_id}_failures.csv`
- `data/ai-proposals/{condition}/ai_proposals_{condition}_{run_id}_failures.csv`
- `data/ai-proposals/{condition}/ai_proposals_{condition}_progress_{run_id}.csv`
  - used only for resumption, debugging, and audit
  - not the main downstream analysis input

For downstream reuse, the key rule is:

- `3_rephrase.ipynb` and `4a_prepare_proposal_for_analysis.ipynb` should be
  able to locate the latest `ai_proposals_{condition}_complete_*.csv` file and
  run from that alone, without needing to reconstruct prompts or reload the
  idea-generation notebook state.

The complete proposal CSV must therefore contain all original proposal text and
all provenance columns needed later, including condition, model, idea-call
structure, persona linkage, prompt-template names, and temperatures.

### 3.8 Condition-Specific Generation Rules

#### `baseline`

- Use one batch prompt per model.
- The model must return exactly `N` ideas in a single JSON object.
- Preserve the returned order and record it in `idea_position_in_call`.
- The full proposal stage should expand each saved idea later using the same
  model, with the minimal proposal-expansion template and temperature `0.9`.

#### `one_at_a_time`

- Use `N` independent idea calls per model.
- Each call must request exactly one idea and only one idea.
- If a response contains zero or more than one parsed idea, mark the call as
  failed and retry rather than silently taking the first record.
- The full proposal stage should expand each saved idea later using the same
  model and the minimal proposal-expansion template.

#### `persona`

- Use `N` persona cards, one matched to each human team/proposal.
- Use `N` independent idea calls per model, one persona card per call.
- The idea row must record the persona card and source human proposal metadata.
- During proposal expansion, reuse the same persona card that produced the idea
  so the condition reflects persona grounding during both idea generation and
  proposal writing, not only the title/abstract step.

### 3.9 Changes Needed In `src/prompt_templates.py`

The current prompt file has the right broad ingredients but not the right
condition structure.

Required changes:

- Keep the existing minimal prompt family as the conceptual base, but split the
  idea-generation templates into explicit condition-aligned variants:
  - `generate_ideas_minimal_batch`
  - `generate_ideas_minimal_single`
  - `generate_ideas_persona_single`

- Do not use the batch prompt by simply setting `num=1` for the
  `one_at_a_time` condition. The single-idea prompt should be written as a true
  one-draw prompt and should not include list-level wording such as "all
  different from each other."

- Keep JSON output requirements strict and identical across idea templates:
  - batch template returns a JSON list of `N` idea objects
  - single templates return a JSON list of exactly one idea object, or one
    single idea object if the parser is updated consistently

- Add a persona-aware proposal-expansion template, for example

## 4. Detailed Redesign For `2_gen_reviews.ipynb`

This section is the concrete redesign spec for the review-generation stage. It
uses the current `notebooks/templates/generate_reviews.ipynb` and its source
scripts only as source material. The new working notebook should be
`notebooks/2_gen_reviews.ipynb`.

The current template notebook is not clean enough for the redesigned study:

- it runs only one condition at a time
- it reviews both AI and human proposals
- it depends on rephrased proposals
- it depends on `proposal_lit_neighbors.json`
- it generates novelty reviews in the same notebook
- it rephrases reviews in the same notebook
- it rebuilds `review_scores_wide.csv` in the same notebook

The redesign should strip all of that out. `2_gen_reviews.ipynb` should become
a true generation notebook.

### 4.1 Scope

`2_gen_reviews.ipynb` should do exactly one study task:

1. Generate AI NCEMS-criteria reviews for each review-generation condition and
   save them as condition-specific CSV files.

It should not:

- review AI-generated proposals
- generate novelty-framework reviews
- rephrase AI reviews
- rebuild `review_scores_wide.csv`
- depend on `compare_proposals_rephrased.ipynb`
- depend on `proposal_lit_neighbors.json`
- perform exact n-matching or any downstream panel sampling

### 4.2 Review Conditions This Notebook Must Support

The notebook should support exactly these review-generation conditions:

- `baseline`
  - review target set: all human proposals only
  - each AI model generates `5` reviews per human proposal
  - one API call returns a structured batch of `5` reviews
  - prompt family: NCEMS criteria only
  - temperature `0.9`

- `one_at_a_time`
  - review target set: all human proposals only
  - each AI model generates `5` reviews per human proposal
  - each review is one independent API call
  - prompt family: NCEMS criteria only
  - temperature `0.9`

- `persona`
  - review target set: all human proposals only
  - each AI model generates `5` reviews per human proposal
  - each review is one independent API call
  - prompt family: NCEMS criteria plus reviewer persona card
  - temperature `0.9`

### 4.3 Non-Negotiable Scientific Design Rules

The current review-generation code conflicts with the redesigned study in
several important ways. The new notebook must follow these rules:

- Review targets are the original human proposals only, not AI proposals.
- AI review generation happens before rephrasing, so the notebook must read the
  original human proposal files, not rephrased proposal files.
- Every condition must generate the full repeated-review reservoir:
  `5 reviews × 3 models × 23 human proposals = 345 AI reviews` per condition.
- Exact matching to the human review count per proposal happens later in
  `4b_prepare_review_for_analysis.ipynb` and `6a/6b_compare_reviews_*.ipynb`,
  not in the generation notebook.
- Cross-condition reuse of cached human-proposal AI reviews should not happen.
  `baseline`, `one_at_a_time`, and `persona` are distinct review-generation
  conditions and each must be generated in full.
- The notebook should preserve all raw repeated reviews. It must not average,
  collapse, or pre-pool them during generation.

This design also resolves the current ambiguity in the top-level review plan
about pooled AI panels of size `9` versus `15`: the generation stage should
always preserve the full `15` raw reviews per proposal (`5` per model), and the
later analysis notebooks can define whatever balanced or pooled panel-sampling
rule is needed.

- `data/human-proposals/human-proposals-y2.json`

The current human proposal files already contain stable `proposal_id` values,
so the redesign should stop using proposal titles as the main join key.

### 4.5 Required Execution Order

The review-generation stage should run in this order:

1. Load the human proposal roster and the observed human review counts.
2. Build a frozen review schedule for each requested condition before making
   model calls.
3. Run the scheduled review calls and save progress incrementally.
4. Validate completeness and only then write the final `complete` CSV.

The frozen schedule matters because it makes repeated-review generation
auditable, especially for the persona condition.

### 4.6 Required Notebook Structure

`notebooks/2_gen_reviews.ipynb` should be structured like this:

1. `## Configuration`
   - choose `REVIEW_CONDITIONS_TO_RUN`
   - choose `MODELS_TO_USE`
   - set `REVIEWS_PER_MODEL_PER_PROPOSAL = 5`
   - set `GENERATION_TEMPERATURE = 0.9`
   - set `MAX_RETRIES`, `SAVE_PROGRESS_EVERY_N_CALLS`, and `RESUME_OK`

2. `## Environment Validation`
   - validate imports and API keys
   - validate required human proposal and human review input files
   - do not run rephrasing or score-building here

3. `## Load Human Proposal Roster`
   - load Y1 and Y2 human proposals
   - build stable target proposal UIDs
   - build the full proposal text used for AI review generation

4. `## Load Human Review Counts`
   - compute the observed human review count for each human proposal from the
     raw human review workbooks
   - attach `target_human_n_reviews` to the target roster

5. `## Build Review Condition Registry`
   - one explicit config object per review condition
   - each config should state:
     - condition name
     - review prompt template
     - whether reviewer persona cards are used
     - whether one call returns one review or a 5-review batch
     - reviews per model per proposal
     - expected number of API calls
     - expected number of review rows

6. `## Build Frozen Review Schedule`
   - create the full planned schedule of review calls before generation
   - save the schedule as a CSV per condition

7. `## Run AI Review Generation`
   - loop over the frozen schedule rows rather than hard-coding one execution
     pattern
   - support both one-review calls and one-call-batch-of-5 responses
   - save progress after each completed API call or parsed batch
   - keep failure logs

8. `## Quality Checks`
   - verify expected counts
   - verify stable IDs and persona assignments
   - verify parse completeness

9. `## Final QA Summary`
   - counts by condition, proposal, model, draw index, and API-call count
   - failures and retries
   - output paths
   - completion status

### 4.10 Condition-Specific Generation Rules

#### `baseline`

- For each human proposal and each model, generate exactly `5` reviews in one
  batched API response.
- The response contract should be a structured list of `5` review objects, not
  one long free-form paragraph.
- The notebook must parse that single response into `5` flat rows with:
  - one shared `review_call_id`
  - `review_draw_index = 1..5`
- If the batch response is incomplete or unparsable, retry the call rather than
  keeping a partial panel.
- The notebook must preserve the fact that these five reviews came from the same
  batched call via `review_generation_mode` and shared call metadata.

#### `one_at_a_time`

- For each human proposal and each model, generate exactly `5` independent
  reviews.
- Each review must be a separate call with its own `review_call_id`.
- Each call should use the same non-persona NCEMS review template.
- If a response is unparsable or missing required fields, the call should be
  logged as a failure and retried rather than silently accepted.
- The notebook must not collapse the 5 draws into one averaged row.

#### `persona`

- For each human proposal and each model, generate exactly `5` independent
  reviews.
- Each review call must include both the NCEMS criteria and a reviewer persona
  card.
- Each review row must preserve the persona metadata that conditioned it.
- The notebook must not collapse the 5 draws into one averaged row.

### 4.11 Reviewer Persona Assignment Rule

The current top-level spec states that persona-conditioned review generation
should simulate reviewer heterogeneity, but it does not yet fully specify how
persona cards should be assigned. The cleanest rule for the redesign is:

- Build one fixed reviewer-persona schedule per target human proposal.
- For each target proposal, assign `5` distinct reviewer personas.
- Exclude the persona card derived from the target proposal's own author team.
- Reuse the same 5-persona schedule across all evaluator models.
- Save this schedule in the condition's `review_schedule_*.csv`.

This is the most defensible design because it changes reviewer perspective while
holding the proposal target and the review-draw structure constant across
models.

The current `eval_ncems_criteria` template is not sufficient for the redesigned
review-generation stage.

- Split the current NCEMS evaluation prompt into explicit review-generation

  - `eval_ncems_criteria_single`
  - `eval_ncems_criteria_persona_single`

- Keep the NCEMS criteria themselves, but revise the output contract so:
  - the batch template maps one model response to five flat review rows
  - the single-review templates map one model response to one flat review row

- The prompt should require both:
  - structured criterion-level scores and justifications
  - direct review text fields: `review_text`, `strengths`, `weakness`,
    `overall_numeric_score`, `overall_summary`

- The persona review template should include a reviewer-persona parameter, for
  example `reviewer_persona_card_json`, and instruct the model to adopt the
  scientific review perspective implied by the card without imitating personal
  prose style or biography.

- Every review-generation prompt should carry a stable template name and a
  prompt-version string that gets written into the output CSV and manifest.

- `eval_novelty` should be removed from the core `2_gen_reviews.ipynb` path.
  If it is kept at all, it should be treated as an appendix-only review family,

## 5. Detailed Redesign For `3_rephrase.ipynb`

There is no existing template notebook for this stage. The redesign should
build `notebooks/3_rephrase.ipynb` around refactored reusable functions from
`src/rephrase_proposals.py` and `src/rephrase_reviews.py`, rather than around
subprocess wrappers of their current CLIs.

This notebook should be the single place where original AI outputs and shared
human outputs are transformed into style-standardized rephrased versions for
the downstream "rephrased" analysis branch.

### 5.1 Scope

`3_rephrase.ipynb` should do exactly these tasks:

1. Rephrase AI proposals for each proposal condition.
2. Rephrase AI reviews for each review condition.
3. Ensure shared human proposals are rephrased once.
4. Ensure shared human reviews are rephrased once.

It should not:

- generate new proposals
- generate new reviews
- build embeddings
- prepare merged analysis tables
- run proposal or review comparisons
- overwrite the original generated files

### 5.2 Main Design Rules

The rephrasing stage should follow these non-negotiable rules:

- Original and rephrased text are both scientifically important outputs.
  Rephrasing should create parallel artifacts, not replacements.
- Rephrasing should be deterministic and standardized.
  The notebook should use one fixed rephrase model and `temperature = 0` for a
  given run, and record that in manifests.
- AI outputs vary by condition and therefore must be rephrased and saved within
  each condition folder.
- Human outputs do not vary by AI condition and therefore should be rephrased
  once centrally and reused across all conditions.
- Stable IDs from the generation stage must be preserved:
  - `proposal_uid` for proposals
  - `review_uid` for reviews
- The rephrase stage must not destroy original structured fields. Rephrased
  fields should be added as new columns, not overwrite original columns.
- The proposal rephrase pipeline and the review rephrase pipeline do different
  jobs and should remain distinct:
  - proposal rephrasing standardizes long scientific proposal text into an
    evaluation-aligned representation
  - review rephrasing standardizes short review prose into neutral summaries of
    the same evaluation

### 5.3 Proposal Rephrasing Rules

For proposals, the current `src/rephrase_proposals.py` pipeline is broadly the
right conceptual starting point and should be retained in refactored form:

- Step 1: summarize the proposal into semantic facts
- Step 2: fill the fixed standardized proposal template from those facts
- Step 3: create the short rephrased abstract used for literature-relative
  analyses

Required redesign rules:

- Keep all original proposal columns unchanged.
- Add rephrased proposal fields as new columns.
- Do not overwrite the original `title`.
- If title rephrasing is ever used, store it as a new field such as
  `rephrased_title`; do not replace `title`.
- The main downstream rephrased proposal fields should be:
  - `standardized_text`
  - `rephrased_abstract`

### 5.4 Review Rephrasing Rules

For reviews, the current `src/rephrase_reviews.py` logic needs a larger
redesign because it still assumes nested JSON AI reviews and ambiguous output
column names.

Required redesign rules:

- The AI review rephrase path must accept the flat review CSVs produced by
  `2_gen_reviews.ipynb`.
- If `review_text`, `strengths`, and `weakness` already exist as direct fields,
  use them directly.
- Do not reconstruct review text from nested evaluation JSON unless running on
  a legacy file for backward compatibility.
- Preserve original review fields unchanged.
- Add rephrased review fields as new columns:
  - `rephrased_review`
  - `rephrased_strengths`
  - `rephrased_weakness`
- Do not overwrite original `strengths` or `weakness`.

### 5.5 Stage Dependencies

`3_rephrase.ipynb` should run after:

- `1_gen_proposals.ipynb`
- `2_gen_reviews.ipynb`

It should not depend on:

- `4a_prepare_proposal_for_analysis.ipynb`
- `4b_prepare_review_for_analysis.ipynb`

The rephrase stage should be able to run as soon as the original AI proposal
and AI review outputs exist.

### 5.6 Required Execution Order

The notebook should run in this order:

1. Validate that the latest original AI proposal and AI review outputs exist
   for the requested conditions.
2. Validate that shared human proposal and human review source files exist.
3. Build a rephrase job registry for AI proposals, AI reviews, human proposals,
   and human reviews.
4. Rephrase AI proposals by condition.
5. Rephrase AI reviews by condition.
6. Rephrase shared human proposals if missing or incomplete.
7. Rephrase shared human reviews if missing or incomplete.
8. Run QA checks and write manifests.

This order keeps the AI condition-specific artifacts and the shared human
artifacts conceptually separate while still allowing one notebook to produce the
full rephrased branch needed downstream.

### 6.7 Embedding, Matrix, and Neighbor Rules

The redesigned `4a` notebook should create reusable numerical artifacts rather
than forcing every comparison notebook to rebuild them.

Proposal-space artifacts:

- create a full-text embedding bundle for each condition and text branch
- create an abstract-only embedding bundle for each condition and text branch
- create a proposal-space pairwise cosine-distance matrix from the full-text
  embeddings
- create a secondary abstract-only pairwise cosine-distance matrix only if later
  analyses need it; otherwise it may remain optional
- fit and save a proposal-space UMAP reducer and 2D coordinates for each
  condition and text branch so later notebooks can reuse the same map instead of
  refitting

Proposal-to-literature artifacts:

- use abstract-only proposal embeddings
- never use full-proposal embeddings for literature-relative analyses
- compute and save a nearest-neighbor cache from proposals to literature
- the cache should include enough neighbors to support every downstream novelty,
  BERTopic-region, MeSH-neighbor, and literature-year analysis without
  recomputing distances
- the chosen `K` should be a single explicit constant in the notebook or helper
  module, set to the maximum `k` needed by downstream analyses

Representation rule:

- proposal-to-proposal diversity comparisons use the full-text embedding bundle
- proposal-to-literature novelty and coverage comparisons use the abstract-only
  embedding bundle

## 7. Detailed Redesign For `4b_prepare_review_for_analysis.ipynb`

It is based primarily on the review portions of the current
`notebooks/templates/prepare_data_for_analysis.ipynb`, plus the downstream
requirements visible in
`notebooks/templates/rephrased/compare_reviews_ncems_criteria.ipynb` and the
audited notes in `docs/plans/analysis_plan.md`.

The new working notebook should be
`notebooks/4b_prepare_review_for_analysis.ipynb`.

### 7.1 Scope

`4b_prepare_review_for_analysis.ipynb` should prepare every review-side artifact
needed by the later review-analysis notebooks for one or more review
conditions.

It should do these things:

- load and harmonize Human reviews plus one condition's AI reviews
- prepare both the `original` and `rephrased` review branches
- build canonical review master tables with stable review IDs
- attach stable target-proposal metadata to every review row
- build exact-n-matching metadata and reusable review sampling frames
- create review embeddings for downstream diversity analyses
- create reusable review matrices and per-proposal panel caches
- create proposal-level review score summary tables for later reuse by proposal
  comparison notebooks if needed

It should not:

- prepare proposal embeddings or literature artifacts
- run review-diversity statistics or manuscript figures
- use title-based fuzzy matching to align Human and AI panels
- collapse repeated AI reviews before the later comparison notebooks choose a
  panel-sampling rule
- re-generate reviews or rephrase reviews

### 7.2 Main Design Rules

- The notebook should support only the review-generation conditions that exist in
  the redesign:
  - `baseline`
  - `one_at_a_time`
  - `persona`

- The core review family is `ncems_criteria` only.

- The notebook should operate at the study stage level, not the old
  `rephrased/{condition}` or `minimal` pipeline layout.

- All alignment between Human and AI reviews must use stable target proposal IDs:
  - `target_proposal_uid`
  - `target_cohort`
  - `target_proposal_id`

- The old fuzzy title-matching logic in
  `compare_reviews_ncems_criteria.ipynb` should not survive into the redesign.

- Review preparation must preserve the repeated-review reservoir:
  - `5` AI reviews per model per target proposal
  - `15` pooled AI reviews per target proposal across the three models

- Exact n-matching should be prepared here as metadata and reusable panel-member
  frames, but the later analysis notebooks should still own the actual
  exhaustive exact-panel enumeration and paired inference steps.

- The notebook must use the observed Human review count per proposal from the
  raw Human review files, not assume a fixed `3`, `4`, or `5`.

- As the current local review workbooks stand on `2026-07-08`, the observed
  Human panel sizes are:
  - Y1: `3-5`
  - Y2: `2-4`

  The redesign must therefore support `n_human_reviews` values from `2` through
  `5`, even if the manuscript text later describes the typical range more
  coarsely.

- Condition-specific prepared review artifacts should live under
  `data/prepared/{condition}/reviews/`.

- Because the same Human review source files are compared against multiple AI
  conditions, some Human rows will be duplicated across condition-specific
  prepared outputs for convenience. That duplication is acceptable as long as

## 8. Detailed Redesign For `5a_compare_proposals_original.ipynb`

### 8.5 Analyses To Mirror From `compare_proposals_all_ai.ipynb`

`5a` should mirror the major all-AI proposal analyses on the original-text
branch.

Required pooled analysis families per condition:

- thematic and cluster structure:
  - LDA topic distribution
  - topic participation
  - Ward cluster membership
  - segregation diagnostics

- proposal-space diversity:
  - mean pairwise distance
  - pairwise bimodality decomposition
  - cross-group alignment
  - within-cluster diversity
  - LOO centroid dispersion
  - global-centroid distance
  - MST dispersion
  - sparseness
  - nearest-neighbor isolation / Chamfer
  - UMAP proposal-space visualization
  - grid entropy
  - diversity summary table

Interpretation rule for proposal-space diversity:

- The notebook should explicitly separate footprint-style metrics from
  local-redundancy metrics rather than presenting all dispersion metrics as six
  independent findings.
- The main local-collapse / redundancy metrics should be:
  - `mean_pairwise distance`
  - `nearest-neighbor isolation / Chamfer`
- The main footprint / occupied-area metric should be:
  - `grid entropy`
- The notebook should interpret the results construct-by-construct:
  - if AI is lower on pairwise / nearest-neighbor metrics but similar on grid
    entropy, the conclusion is denser local redundancy without a major footprint
    shrinkage
  - if AI is lower on both the redundancy metrics and grid entropy, the
    conclusion is both local collapse and reduced occupied area
- Metrics such as `centroid_loo`, `global-centroid distance`, `MST dispersion`,
  `sparseness`, `within-cluster diversity`, and `pairwise bimodality
  decomposition` should be treated as exploratory or diagnostic follow-ups
  rather than independent headline confirmations.

- literature-relative novelty and coverage:
  - element novelty percentiles
  - mean-kNN novelty
  - local-density normalized novelty
  - literature-space outlier prevalence
  - literature-anchored UMAP
  - BERTopic region coverage
  - MeSH term coverage
  - literature-neighbor publication-year recency

- style:
  - feature-level Human vs All-AI contrasts
  - style-only classifier with permutation test

The pooled metric definitions should remain aligned with the current audited
binary notebook unless there is a scientifically necessary redesign already
called out elsewhere in this spec.

The notebook should also export a proposal-diversity metric-correlation table or
figure so the manuscript can state clearly which metrics are redundant views of
the same collapse pattern and which capture a distinct construct such as area
coverage.

### 8.6 Inference Rules

`5a` must follow the same inferential cleanup already required elsewhere in the
study:

- for matrix-derived proposal metrics, primary inference must be permutation-
  based
- the permutation p-value is the headline value
- any Mann-Whitney value should be retained only as secondary descriptive

### 10.4 Exact-N Matching And Exhaustive Panel Enumeration Rule

- the per-model AI side samples `n_human_reviews` reviews without replacement

## 11. Detailed Redesign For `6b_compare_reviews_rephrased.ipynb`

### 11.3 Reuse Of Exact-N Panel-Combination Caches From `6a`

  exact-n panel-combination cache and save the rephrased-branch cache locally
